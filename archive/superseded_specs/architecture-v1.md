# Chron-OS Causal Kernel Architecture Specification (V1)

## 1. 概要 (Philosophy & Scope)
Chron-OS は、確率的推論モジュール（LLM）の揺らぎや破綻を「構造的異常（Structural Fault）」として定義し、OSカーネルの因果層（Canonical History）を一切汚染させることなく制御するシステムアーキテクチャである。

本システムは「意味論（Semantics）」をOSの意思決定から完全にパージし、決定論的な「因果（Causality）」のみで状態遷移と世界の歴史（Write-Ahead Log: WAL）を維持する。

## 2. システム層の凍結 (Phase A - F)
Chron-OSの因果カーネルは、以下の6つのフェーズによる一方向のデータフローで構成される。

* **Phase A (Schema):** Event ABIの定義。システム内で発生する全ての事象は、不変の構造体として型定義される。
* **Phase B (WAL):** 永続化。意味を削ぎ落とした「構造ラベル」と「イベント」のみを1次元の単調増加ログとしてストレージに書き込む。
* **Phase C (Reducer):** 状態還元。WALからログをリプレイし、論理状態（Retryカウンタ等）の復元と、必要に応じた物理コンテキストのリセットを行う。
* **Phase D (Lifting):** グラフ構築。1次元のWALから因果のネットワーク（有向非巡回グラフ: DAG）を持ち上げ、クリーンな世界線を抽出する。
* **Phase E (Observation):** 観測。LLMの出力から、意味を読まずに構造的特徴（対称性、エントロピー、トポロジー）のみを抽出・ラベル付けする。
* **Phase F (Control):** 制御。Phase Eの構造ラベルとPhase Cの論理状態に基づき、以下の5つの決定論的な状態遷移アクションのいずれかへルーティングする。
  * `:commit` (正常な対話としてWALに採用する)
  * `:discard` (構造異常により破棄。WALにイベントを発行しないため、クロックは進まない)
  * `:retry` (単純な再試行)
  * `:retry-with-penalty` (サンプラーへのペナルティを伴う再試行)
  * `:abort` (回復不能な破綻として処理を遮断し、`event:structural-fault` をWALに発行してクロックを進める)

## 3. Event ABI (ABI Specification)
カーネルが認識するイベントは、純粋な因果として記録される。全イベントは共通ヘッダを持ち、必要に応じてペイロードスロットが付与される。

### 3.1 共通ヘッダ (Common Header)
すべてのイベント構造体は、因果を保証するための以下のベースフィールドを必ず保持する。
* `kind`: イベントの種別（Keyword）
* `index`: WAL上の絶対シーケンス番号
* `clock`: Lamportクロック（単調増加の論理時計）
* `causal-id`: 因果系列（世界線）の識別子
* `timestamp`: 物理時間のタイムスタンプ

### 3.2 構造的異常イベント (`event:structural-fault`)
LLMの意味論的暴走や生成ループを記録するイベント。
* `kind`: `:structural-fault`
* `ref`: 以下のいずれかの構造ラベル
  * `:echo` (入出力長の完全な対称性と重複)
  * `:stagnation` (トークン多様性の喪失、局所ループ)
  * `:drift` (コンテキスト消費速度の幾何学的異常)
  * `:discontinuity` (直前の履歴空間からのトポロジー的乖離)
* `clock`: `prev_clock + 1` (Lamportクロックを必ず進める)

### 3.3 ツール例外イベント (`event:tool-fault`)
LLMの能力破綻とは区別される、外部環境・ツールの実行失敗（I/Oエラー、ネットワークタイムアウト等）。
* `kind`: `:tool-fault`
* `ref`: ツール側のエラーコード等
* **因果的扱い:** 本イベントは外部環境の例外であり、LLMの構造異常とは独立して扱う。Phase F におけるLLMの `retry-count` には加算されず、ツール側の再試行ポリシー等の別系統として処理される。

## 4. Graph スキーマと論理/物理の分離
Phase D で構築される因果グラフは、WALから持ち上げられた（Lifting）ノードとエッジによって構成される。

### 4.1 Graph ノードの分類 (Event Class)
WAL上のイベントはGraph構築時に以下のいずれかのクラスに分類され、LLMへの射影（Lifting）規則が適用される。
* **`:dialogue`**: ユーザー/アシスタント/システム発話（射影規則: **INCLUDE**）
* **`:tool`**: ツール呼び出し/結果、および `event:tool-fault`（射影規則: 原則 **EXCLUDE**。LLMの文脈には入れない）
* **`:meta`**: OS内部状態（射影規則: **EXCLUDE**）
* **`:fault`**: `event:structural-fault` 専用クラス（射影規則: **EXCLUDE & TERMINATE**。ノード自体を含めず、探索も打ち切る）

### 4.2 エッジの分離
* **`:temporal` (時間的連続エッジ):** WAL上での物理的な記録順序（Happens-Before）を証明する。`event:structural-fault` は旧系列の終端としてこのエッジのみを持ち、新系列の因果親にはならない。
* **`:causal` (論理的依存エッジ):** 意味的な世界線を継承する。新しい対話（新 `causal-id`）の起点ノードは、破綻を起こす直前の「最後の健全な対話ノード」に対してこのエッジを張る。

### 4.3 再ハイドレーション (Re-hydration)
閾値到達による `:abort` 発生時、システムは以下の手順でLLMの物理状態を再起動する。
1. **物理リセット:** LLMの推論エンジン（KVキャッシュ等の物理メモリ）を完全に焼却・解放する。
2. **逆行探索:** Graphの新しい Root ノードから `:causal` エッジのみを過去へ辿る。
3. **枝刈り:** 探索は `:causal` エッジのみに依存するため、`:fault` クラスのノード（`:temporal` でしか繋がっていない）は構造的に無視され、常に「健全だった並行世界」だけが抽出される。
4. **注入 (Prefill):** 抽出したクリーンな履歴をシリアライズし、空のLLMコンテキストへ一括ロードする。

## 5. 周辺仕様およびエッジケース処理方針

### 5.1 グローバル Lamport クロックの単調増加性
Lamportクロックは、システム全体で単調増加するグローバルな論理時計とする。`causal-id` ごとの局所クロックは持たず、並行する複数セッションのイベントに対してもWAL上で厳密な全順序（Total Ordering）を保証する。

### 5.2 未確定生成（部分コミット）の完全パージ
Phase E/F で `:abort` または `:discard` と判定された「途中まで生成された不完全なトークン列」は、Canonical History (WAL) には一切記録しない。事象としては存在しなかったものとして扱い、破綻という構造的事実（`:structural-fault`）のみをコミットする。

### 5.3 再試行（Retry）の冪等性
`:retry` ループの途中で発生した一時的な失敗テキストはWALに書き込まない。最終的に検証をパスした「成功（`:dialogue`）」、または上限に達した「破綻（`:structural-fault`）」のみをコミットすることで、再生（Replay）時の副作用とオーバーヘッドを排除する。

### 5.4 オブザーバビリティ層の独立
WALには純粋な因果のみが記録されるため、開発・監査目的の詳細な情報（破綻した生トークン列、内部の推論スコア等）は、因果カーネルの決定論的状態を一切汚染しない「完全に独立した外部ログ層（リングバッファ、標準出力等）」へ片方向ストリームとして出力することを推奨する。
