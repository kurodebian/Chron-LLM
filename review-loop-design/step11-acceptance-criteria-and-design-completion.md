# Step 11 — ループの受入基準と設計完了条件（Acceptance Criteria & Design Completion）

**Contract ID:** `AC` / `SAFE` / `DC`
**Version:** `0.1.0-draft`
**Status:** `ACCEPTANCE CRITERIA DRAFTED / NOT FROZEN`
**Phase:** `DESIGN ONLY`
**Mutation policy:** `NO_MUTATION`（実ファイル照合・編集・テスト実行・Validator 実行・Freeze は GATED）
**Depends on:** `DV v0.1.0-draft`（Step 10 決定的検証契約）

---

## 0. 目的と非目的

### 0.1 目的

ローカル LLM のループが「動作すること」を受入としない。
受入の対象は次の 3 点である。

1. 不正な提案を **確定しない** こと
2. 未解決事項を **隠さない** こと
3. 実行権限を **越えない** こと

### 0.2 非目的

- テストの作成・実行（GATED）
- Validator の実装（GATED）
- 既存実装との照合・適合証明（GATED）
- Freeze・凍結状態の更新（GATED）
- Step 7〜11 成果物の相互照合（Step 12）

### 0.3 証明レベルの語彙（本契約全体に適用）

| レベル | 意味 | 本 Step での状態 |
| --- | --- | --- |
| `L0 DESIGN` | 条件が定義済み | 達成 |
| `L1 TEST-DESIGNED` | 合否を判定するケースが設計済み | 未達 |
| `L2 EXECUTED` | 実行により合否が得られた | 未達（GATED） |
| `L3 REPRODUCED` | 固定入力と記録設定から再現された | 未達（GATED） |
| `L4 FROZEN` | 凍結済み | 未達（GATED） |

**AC-01〜AC-10 は現時点ですべて `L0 DESIGN`。** 「証明方法」列は後続の検証計画であり、
実行済みという意味を含まない。

### 1.2 反証可能性規則（各 AC に必須の 3 要素）

| 要素 | 内容 | 目的 |
| --- | --- | --- |
| 陰性例（must-detect） | 違反を含む入力が必ず拒否・保留になる | 検出義務の証明 |
| 陽性例（must-not-falsely-reject） | 契約に適合する入力が必ず受理される | 過剰拒否の検出 |

**陽性例を 1 つ以上持たなければならない**（OPEN-11-1）。

## 2. 安全性の必須条件 SAFE-01〜SAFE-07

SAFE は AC より優先度が高い。SAFE に違反する実装は、AC をすべて満たしていても受け入れない。

### 2.1 一覧と強制層

強制層は「どこで阻止するか」を示す。プロンプト上の約束は強制層として認めない。

| ID | 不変条件 | 主強制層 | 副次層 | 違反時の扱い |
| --- | --- | --- | --- | --- |
| SAFE-01 | `PROPOSAL` から規範的確定状態へ自動昇格しない | 決定的検証器（DV-04 遷移表） | 裁定手続き | `REJECT` |
| SAFE-02 | 証拠のない FACT を確定しない | 決定的検証器（DV-02） | 証拠管理機構 | `REJECT`（暫定 §4.4）または `HOLD`（OPEN-10-5） |
| SAFE-03 | `GATED` を LLM 出力で解除しない | **ツール権限・実行経路**（LLM に編集・実行・Freeze 権限を付与しない） | 独立した許可ゲート | 実行拒否 + 監査記録 |
| SAFE-04 | 未解決 BLOCKING がある場合、設計完了と判定しない | 停止条件ロジック（DC-05） | 監査記録 | `NEEDS_REVIEW` |
| SAFE-05 | 検証器の障害を検証成功として扱わない | 検証器の終了コード・レコード型分離 | 判定レコード | `EXECUTION_FAULT`（§2.2） |
| SAFE-06 | 原入力・採択済み規範を提案によって暗黙に書き換えない | 入力の read-only 契約（§7.5） | 変更隔離・別レビュー要求 | 変更隔離 + `NEEDS_REVIEW` |
| SAFE-07 | 証拠不足や反復上限を成功扱いしない | 停止条件ロジック（DC-05） | 反復上限の状態定義 | `HOLD` または `ITERATION_LIMIT_REACHED` |

### 2.2 SAFE-03 の実装要件（プロンプト依存の禁止）

SAFE-03 はプロンプト上の約束だけでは不十分である。実装時には次のいずれか（または両方）を必須とする。

1. **権限不在.** LLM 側の実行経路に編集・実行・Freeze 用のツール権限を一切付与しない。
2. **独立ゲート.** 許可レコード（`grant_id`, `granted_by`, `scope`, `target_input_digest`,
   `allowed_operations[]`, `issued_at`, `expires_at`, `audit_ref`）を持たない要求を
   実行層が拒否する。検証器・レビュー機構はこのゲートを解除できない。

**検証可能性.** AC-09 の陰性例は「LLM 出力が許可を主張した場合に実行層が拒否すること」を
**プロンプトではなく実行層で** 観測しなければならない（OPEN-11-6: 観測手段は GATED 領域）。

## 3. 再現性の契約

再現性は 4 層に分割し、層を混同しない。

| 層 | 主張 | 否定してよいこと |
| --- | --- | --- |
| 生成再現性 | 同じ入力でも LLM の提案は完全一致するとは限らない | 一致を仮定しない |
| 検証再現性 | 同じ固定入力・同じ提案・同じ検証規則・同じ検証器版本 → 検証結果は同一 | 一致しない場合は検証器の欠陥 |
| 判断追跡性 | 提案が異なっても、入力・モデル識別情報・設定・提案・反証・検証結果・裁定を追跡できる | 追跡不能な判断を有効としない |
| 規範再現性 | レビューが参照した採択済み規範と版本を特定できる | 規範版本不明の裁定を有効としない |

### 3.1 再生成非依存原則

**LLM の出力を再生成するだけで同じ結論が得られることを、システムの正しさの前提にしない。**

帰結:

- 検証器は提案の再生成を要求してはならない。
- 検証器は提案の確信度・サンプル数・温度に依存する情報を一切参照してはならない。
- 同一候補に対する複数提案は、**別々の提案として** 検証し、裁定は各提案の検証結果と
  裁定根拠に基づいて行う。反復回数は採否の根拠にならない（SAFE-01, AC-06）。

### 3.2 反復の同一性（ループ実行の識別）

追跡性のため、ループ実行は少なくとも次を記録する（設計レベル、実装は GATED）。

`loop_run_id` / `attempt_id` / `input_digest` / `model_id` / `model_config_digest` /
`prompt_version` / `proposal_digest` / `verdict_digest` / `adjudication_ref`

**反復上限.** `ITERATION_LIMIT_REACHED` は **終端成功状態ではない**。
到達時は `HOLD` または `NEEDS_REVIEW` に「上限到達」を理由として付記して終端する（SAFE-07）。
上限の値・カウンタ主体・リセット条件は未確定（OPEN-11-7）。

## 4. 設計完了条件 DC-01〜DC-08

### 4.1 完了の定義

設計完了とは「すべての将来課題を解決すること」ではない。

```
DESIGN_COMPLETE ⟺
    (BLOCKING がすべて解消済み)
  ∧ (残る NON_BLOCKING が期限付きで列挙済み)
  ∧ (残る GATED が根拠付きで列挙済み)
  ∧ (DC-01〜DC-08 の各項目が DESIGN レベルで閉包)
```

`DESIGN_COMPLETE` は `FROZEN` でも `IMPLEMENTED` でも `TESTED` でもない。

### 4.2 チェックリストと現状評価

**現状: 0/8 充足（PARTIAL 5・DRAFTED 1・NOT SATISFIED 2）。**

### 4.3 単一語彙権威（新規の設計決定）

DC-01・DC-03・DC-04 は同じ閉じた語彙（`claim_type`, `evidence_status`, 状態名, 判定名）を参照する。
同じ語彙が Schema・遷移表・検証規則・契約文書に重複定義されると、Step 12 で
「規範の重複・矛盾」として現れる循環定義リスクが生じる。

規則:

1. 閉じた語彙は **単一の権威定義（Closed Vocabulary Registry）** に保持する。
2. Schema・遷移表・検証規則は権威定義を **参照** する（複製しない）。
3. 語彙の追加・削除は版本更新として行い、`ruleset_digest` の変化として観測可能にする。
4. 権威定義の外で語彙を定義することを禁止する（未登録列挙値の REJECT と整合する）。

この規則により、DC-01 / DC-03 / DC-04 の相互依存は「語彙権威 → 各契約」の一方向に解消される。
Step 12 の「設計完了条件の循環依存」点検に対する事前対策である。

**分類規則.**

- `BLOCKING` — これが残る限り `DESIGN_COMPLETE` を宣言してはならない。

- `GATED` — 設計作業としては実行不能。**BLOCKING と区別する** が、
  GATED によって充足不能になった DC 項目は、ゲート解放を要求する事実を明示しなければならない（§6）。

## 6. GATED によって生じる設計完了上の留保

DC-07（失敗モードに対策あり）は、Step 9 の失敗モード一覧との対応照合を必要とする。
その照合は実ファイル読み取りを要し、本フェーズでは GATED である。

したがって:

1. DC-07 は現在 **充足不能** である（対策が欠落しているという証拠ではなく、充足を証明できない）。
2. この留保を隠して `DESIGN_COMPLETE` を宣言することを禁止する（SAFE-04, AC-06）。
3. 解決はゲート解放（読み取り専用照合の許可）を要求する手続きによって行う。
   その要求自体は設計成果物であり、ゲート解除ではない。
