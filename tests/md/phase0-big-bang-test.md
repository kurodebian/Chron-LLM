# Phase 0 Big Bang Test Specification (`chron-llm/tests/phase0`)

## Overview
This package defines a test suite for the "Phase 0 Big Bang" scenario. Its primary purpose is to verify the integrity of the **4-layer unified pipeline** sequence and world state transitions during initial execution using a mocked observation provider.

## Public API

### `run-phase0-big-bang-test`
Executes the end-to-end verification test for the Phase 0 initialization logic.

*   **Parameters:** None.
*   **Return Value:** 
    *   Returns `t` if all assertions pass and execution completes successfully.
    *   Signals an error (via `assert`) if any invariant is violated.
*   **Side Effects:** Prints a verification success message to standard output (`T`).

## Internal Components

### Structure: `test-mock-provider`
A mock structure used to simulate external observation fetching during tests.

*   **Fields:**
    *   `input-sequence`: A list of strings representing pre-defined responses (default: `nil`).
    *   `execution-log`: A list recording executed actions for verification (default: `nil`).

### Method: `fetch-observation` (Specialized)
Implements the observation fetching interface for `test-mock-provider`.

*   **Signature:** `(chron-llm/r1:fetch-observation provider action)`
*   **Logic:**
    1.  Logs the physical action type of the provided `action` into the provider's execution log.
    2.  Pops the next text string from the provider's `input-sequence`.
    3.  Returns a new inference observation object (`chron-llm/r2-1-b:make-inference-observation`) containing:
        *   `raw-text`: The popped text or `"default-test-fact"` if sequence is empty.
        *   `finish-reason`: `:stop`
        *   `config`: `'(:mode :test)`
        *   `provider-metadata`: `'(:provider :test-mock)`

## Execution Logic & Control Flow

The function `run-phase0-big-bang-test` follows this deterministic sequence:

1.  **Initialization:**
    *   Creates a `genesis` world state with causal-id `"genesis"`.
    *   Instantiates a `test-mock-provider` seeded with inputs `("hello" "world")`.
    *   Initializes a counter generator and a bootstrap observation.

2.  **Pipeline Loop (2 Iterations):**
    For each iteration, the system executes the unified pipeline:
    *   **Evaluation:** Calls `evaluate-observation` to generate a decision based on current world state and observation.
    *   **Derivation:** Calls `derive-ops` to determine operations from the decision.
    *   **Scheduling:** Calls `scheduler-step` to produce a new world state and an action using a generated causal ID.

3.  **State Update:**
    *   Updates `current-world` to the newly scheduled world state.
    *   Fetches the next observation via the mock provider based on the generated action.

## Invariants & Assertions

The test enforces specific invariants at runtime:

### Loop Invariants (Per Iteration)
1.  **Causal Lineage:** The causal ID of the `current-world` must match the parent ID of the `new-world`.
2.  **Action Type:** The physical action type generated by the scheduler must be exactly `:invoke-api`.

### Final State Invariants (Post-Loop)
1.  **Final Causal ID:** The causal ID of the final world state must equal `"node-2"`.
2.  **Retry Count:** The retry count of the final world state must equal `2`.
